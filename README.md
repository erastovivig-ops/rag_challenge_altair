# LLM + RAG Challenge: Исследователь по источникам

Проект представляет собой реализацию **RAG-системы (Retrieval-Augmented Generation)**, предназначенной для поиска ответов на вопросы пользователя по собственной базе документов с обязательным указанием точных источников и с базовой защитой от галлюцинаций.


## 1. Что сделали?

В ходе выполнения челленджа была спроектирована и реализована полная цепочка RAG:

  

 ### Вопрос⟶retrieve()⟶Top-k chunks⟶build_context()⟶build_prompt()⟶ask_llm()⟶Ответ



### Основные этапы работы:

1. **Подготовка данных и чанкинг (Chunking):**
    
      
    - Сформирована собственная база знаний из 3 предметных источников:
        
          
        - `Операционные_системы.txt` (управление ресурсами, процессы, примитивы синхронизации);
            
              
            
        - `Компьютерные_сети.txt` (модель OSI, стек TCP/IP, прикладные протоколы);
            
              
            
        - `Алгоритмы_и_структуры_данных.txt` (базовые структуры, Big O нотация, алгоритмы сортировки и поиска).
            
              
            
    - Реализован механизм разбиения текстов на чанки с использованием скользящего окна (размер чанка и перекрытие).
        
          
        
2. **Векторизация и Поиск (Retrieval):**
    
      
    - Выполнена векторизация текстов с помощью эмбеддинг-модели `sentence-transformers/all-MiniLM-L6-v2` (а также протестирована `paraphrase-multilingual-MiniLM-L12-v2`).
        
          
        
    - Настроен быстрый векторный поиск через **FAISS** (`IndexFlatL2`), возвращающий `top_k` наиболее релевантных фрагментов со скорами расстояния/сходства.
        
          
        
3. **Фильтрация и сборка контекста (Context & Thresholding):**
    
      
    - Добавлен порог релевантности (`retrieve_with_threshold`). Если лучший результат превышает порог расстояния (недостаточно релевантен), система мгновенно возвращает сообщения о нехватке данных, **не задействуя LLM** (что экономит ресурсы и предотвращает лишние вызовы API).
        
          
        
    - Реализована функция `build_context()`, форматирующая релевантные чанки с явным указанием названия файла-источника `[Источник: filename.txt]`.
        
          
        
4. **Промпт-инжиниринг и интеграция с LLM:**
    
      
    - Сконструирован строгий системный промпт (`build_prompt`), обязывающий языковую модель (`openai/gpt-oss-20b` через Hugging Face Inference API):
        
          
        1. Использовать **только** представленный контекст.
            
              
            
        2. Всегда указывать имена файлов-источников при ответе.
            
              
            
        3. Отвечать «Не знаю» / «В источниках нет информации», если контекст не содержит прямого ответа.
            
              
            

## 2. Как проверяли?

Тестирование проводилось в два этапа: сначала на базовых demo-текстах, затем на созданной технической базе знаний по Computer Science. Набор тестов включал 5 разноплановых сценариев:

  

1. **Вопрос с явным ответом в одном источнике (Single-source):**
    
      
    - _Пример:_ «Чем отличается TCP от UDP?»
        
          
        
    - _Результат:_ Поисковик точно находит чанк `Компьютерные_сети.txt`, модель выдаёт верный ответ со ссылкой на источник.
        
          
        
2. **Вопрос, требующий синтеза из нескольких источников (Multi-source):**
    
      
    - _Пример:_ «Как оценить эффективность алгоритма и какие протоколы гарантируют надежную доставку данных?»
        
          
        
    - _Результат:_ Поисковик извлекает релевантные фрагменты из `Алгоритмы_и_структуры_данных.txt` и `Компьютерные_сети.txt`. Модель объединяет факты в один логичный ответ с двумя ссылками.
        
          
        
3. **Вопрос на отсутствие информации в базе (Out-of-domain):**
    
      
    - _Пример:_ «Какая библиотека используется для реализации мьютексов в ОС?»
        
          
        
    - _Результат:_ Фрагменты по ОС находятся, но в них нет конкретного названия библиотеки. Модель строго соблюдает инструкции и отвечает `не знаю`.
        
          
        
4. **Запрос, полностью нерелевантный тематике базы:**
    
      
    - _Пример:_ «Какой рецепт приготовления пасты Карбонара?»
        
          
        
    - _Результат:_ Отрабатывает `retrieve_with_threshold`, блокирует вызов LLM и возвращает ответ о falta данных в базе.
        
          
        
5. **Вопрос с косвенной формулировкой / синонимией:**
    
      
    - _Пример:_ «Как избежать состояния гонки при параллельном выполнении задач?»
        
          
        
    - _Результат:_ Эмбеддинги успешно сопоставляют семантику, находится чанк про мьютексы и семафоры в ОС.
        
          
        

## 3. Где система ошибается?

Несмотря на успешные тесты, в текущей архитектуре выявлены следующие ограничении и узкие места:

  

1. **Ограничения семантического поиска при точечных деталях:**
    
      
    - Если запрос содержит специфический термин или аббревиатуру, которой нет в обучающем датасете векторной модели, косинусное сходство может быть низким (проблема Pure Dense Retrieval).
        
          
        
2. **Границы чанков (Chunk Boundary Issue):**
    
      
    - При фиксированном размере окна важный контекст или связное предложение может оказаться разрезанным между двумя чанками, из-за чего теряется смысловая целостность.
        
          
        
3. **Потеря порядка и структуры:**
    
      
    - Простой векторный поиск не учитывает иерархию документа (разделы, заголовки, таблицы). Ответ на вопрос, требующий понимания структуры текста, может быть неполным.
        
          
        
4. **Зависимость от порога (`threshold`):**
    
      
    - Фиксированный `threshold` для расстояния FAISS L2 / Cosine Similarity может работать нестабильно: для коротких запросов скоры отличаются от длинных, что может приводить либо к пропуску нужных чанков (False Negative), либо к пропуску шума (False Positive).
        
          
        

## 4. Что улучшили бы дальше?

Для перевода системы в продакшен-уровень планируются следующие улучшения:

  

1. **Гибридный поиск (Hybrid Search):**
    
      
    - Объединить векторный поиск (Dense Retrieval) с ключевым поиском BM25 (Sparse Retrieval) с помощью алгоритма **Reciprocal Rank Fusion (RRF)**. Это позволит искать как по смыслу, так и по точным совпадениям терминов/кода.
        
          
        
2. **Реренкинг (Reranking):**
    
      
    - Добавить этап **Cross-Encoder Reranker** (например, `bge-reranker-large`) после первичного поиска Top-10/20 чанков. Это существенно повысит точность ранжирования Top-k чанков, передаваемых в LLM.
        
          
        
3. **Умный чанкинг (Semantic / Structural Chunking):**
    
      
    - Перейти от простого разделения по словам/символам к разбиению по логическим секциям (Markdown-заголовки, абзацы) или использовать `SemanticChunker` из LangChain/LlamaIndex.
        
          
        
4. **Продвинутый промпт-инжиниринг и Guardrails:**
    
      
    - Внедрить валидацию ответов через `Pydantic` или спец-фреймворки (Guardrails AI) для гарантированного форматирования вывода (например, JSON с отдельными полями `answer` и `sources`).
        
          
        
5. **Оценка качества (RAG Triad Evaluation):**
    
      
    - Подключить метрики оценки RAG (с использованием `Ragas` или `TruLens`) для автоматического измерения:
        
          
        - **Context Relevance** (релевантность найденных чанков);
            
              
            
        - **Groundedness / Faithfulness** (отсутствие галлюцинаций);
            
              
            
        - **Answer Relevance** (соответствие ответа исходному вопросу).
